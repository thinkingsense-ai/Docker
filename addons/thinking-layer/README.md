# Thinking layer (phase 2 skeleton, plus what the phase 3 UI needs)

The small service between the front-ends (Agency, later Ask and Claude) and the OmniGate Server. See [docs/agency-spec.md](../../docs/agency-spec.md) section 4 and
[docs/agency-design.md](../../docs/agency-design.md). Standard library Python, no dependencies, no database.

What works now:

| Route | What |
|---|---|
| `POST /login`, `POST /logout`, `GET /whoami` | Signs in to the Server's business-user login; the layer holds the Server's cookie and gives the browser its own `HttpOnly` cookie |
| `GET /packs` | The pack catalogue (`packs/catalogue.json`) with whether each pack is loaded: a Workspace named for it, an approved-question category, or unknown |
| `POST /ask` | Sets the session's Workspace to the pack (or the default for All data), asks, and returns the answer with an **evidence block**; with `Accept: text/event-stream` it relays the Server's events and puts an `evidence` event just before `done` |
| `GET /decisions?runId=` | The hash-chained decision record for a run the Server shows this user, with the chain verified here. Needs `AGENCY_DECISION_FILE` (the Server's `OMNIGATE_WORKFLOW_DECISION_FILE`, shared read-only) |
| `GET /starters?pack=`, `GET /conversations`, `GET /conversations/get?id=` | Pass-through to the Server's starter questions (only catalogue pack ids are forwarded) and the signed-in user's conversations; the id is URL-encoded |
| `GET/POST /preferences` | Per-user preference (`pack` only, validated) keyed by Server username; in memory, or a JSON file when `AGENCY_PREFS_FILE` is set |
| `GET /` and other non-API paths | The built Agency UI from `AGENCY_WEB_DIST` (single-page fallback, path-escape safe, CSP `default-src 'self'`); never for `/app/` or `/api/` |
| `GET /adapters`, `POST /uploads?name=&workspaceId=` (raw body), `GET /uploads[/id]`, `DELETE /uploads/id` | Upload adapters (below) and the caller's own upload records |
| `GET /status`, `GET /tools`, `GET /health` | Reachability, whether the workflow routes exist (the free edition answers 404), and the tool list generated from `contract.json` |

Run the tests (a fake Server stands in): `python3 -m unittest discover -s addons/thinking-layer/tests` from the repository root.
Run beside a pack stack: see `docker-compose.layer.yml`.

Things to know:
- **Scope.** The Server limits a Workspace by data source, not schema (Server#109), and on today's stacks no Workspace exists for a pack until the generated `packs/workspaces.yaml` is loaded. The evidence block says which case applied: `server-backends`, `agency-hint` (opt-in `AGENCY_SCOPE_HINT=on`, which appends the pack's data sets to the question; its effect on accuracy is **not measured**) or `none`.
- **One question at a time per session**, because the Workspace is session state on the Server.
- **Decisions.** The Server has no business-user route for the decision record in v0.10.19, so the layer reads the shared file. A route would remove that; to raise with Kumar.
- **Edition.** The Server does not report its edition to business users; `/status` infers "workflows available" from the workflow route answering.
- The layer logs no question text and no file content. Sessions are in memory (a restart signs everyone out).
- The UI is `agency/web` (see its README); the Dockerfile builds it and the layer serves it on the same port.
- **Adapters** are separate services named in `AGENCY_ADAPTERS` (comma-separated base URLs; request bodies never name one, so no caller-chosen fetches). An adapter answers `GET /adapter` (manifest: id, title, kind, accepted extensions and MIME types, `maxBytes`, `nonCommercial`, licence, notes) and `POST /ingest` (raw file body, `X-Filename`) with `{result, notes, licence, askPrompts}`. The layer checks the type and size from headers before reading the body, requires the user's `canUploadFiles` grant (from `/app/whoami`), forwards the file, **drops it**, and keeps only the derived record, private to the uploader, for `AGENCY_UPLOAD_HOURS` (default 1; 20 per user; in memory). An unreachable adapter is listed disabled and uploads are off. **Sharing (spec FR-17a)** is off unless `AGENCY_UPLOAD_SHARING=workspace`. The owner can share one of their records into the Workspace it was uploaded in (`POST /uploads/{id}/share {"shared": true|false}`; with no Workspace given an upload goes to `all-data` when the stack has one, otherwise it cannot be shared). Other signed-in users see it, read-only, under `shared` in `GET /uploads` (and `GET /uploads/{id}`) only if **their own Server session lists that Workspace**, so the Server's access rules decide who sees it and sharing never widens them; the owner must themselves be able to use the Workspace. Shared views show who shared it and when, and drop any GPS position and its note. Sharing does not extend the expiry; turning the setting off or losing the Workspace hides the record again. Only the owner can share or delete; `AGENCY_UPLOAD_ADMINS` (comma-separated Server usernames) may also unshare or delete a *shared* record and see all shared records, never a private one. The grant to upload is unchanged: viewing needs none, uploading still needs `canUploadFiles`. The adapters are `demos/audio-demo` and `addons/table-adapter` (CSV/XLSX, describes the table only) `addons/document-adapter` (PDF/DOCX/Markdown/text, describes the text only) and `addons/image-adapter` (JPEG/PNG/GIF/WebP, describes the file only, no model); `AGENCY_ADAPTERS` takes them comma-separated (`/adapter`, `/ingest`); run it with `AGENCY_ADAPTERS=http://audio-service:8090` beside `demos/sounds-pack/docker-compose.audio.yml`. `upload_file` is not an MCP tool (a model cannot hand over file bytes).
- **Workflows (spec FR-24 to FR-28)** relay the Server's workflow API (app v0.10.19 or later, commercial edition, off unless the operator set `OMNIGATE_WORKFLOW_ENGINE`; `docs/workflows-api.md` in the Server repo): `GET /workflows/definitions`, `GET /workflows/queue` ("Waiting for me"), `GET /workflows/{id}`, `POST /workflows/start {definition, key}`, `POST /workflows/{id}/approve {payloadHash}`, `POST /workflows/{id}/reject {reason}`; the decision record is `GET /decisions?runId=`. The layer acts as the signed-in user and sends upstream **only** the whitelisted fields (never a user name), validates ids and hashes before anything is sent, and reshapes errors to `{error:{code,message,detail}}` keeping the Server's code and status (`missing_grant` with `detail.grant`, `initiator_cannot_approve`, `non_human_identity`, `already_approved`, `not_an_approver`, `payload_hash_mismatch` 409, `not_awaiting_approval` 409, `engine_unavailable` 502). A Server 404 with no code becomes `workflows_off`. The Server enforces every rule; the layer enforces none of its own. Read operations are MCP tools (`list_workflow_definitions`, `list_workflows`, `get_workflow_run`); **starting, approving and rejecting are not tools**: they stay human actions in a person's session. The decision record comes from the Server itself on app 0.10.20 and later (`GET /app/workflows/runs/{id}/decisions`, same access as reading the run): `GET /decisions?runId=` relays it, adds `entriesVerified` (the layer recomputed every returned entry's hash; the chain verdict `chainValid` stays the Server's own statement, since a run's entries are a slice of one chain) and `source: "server"`. Against an older Server the layer reads the Server's decision file instead, shared read-only as `AGENCY_DECISION_FILE` (`source: "file"`); with neither, `501 decisions_unavailable`. `GET /status` takes `edition` (free or commercial) and whether workflows exist from `/app/whoami` on 0.10.20 and later, and probes the workflow routes on an older Server. The Server's local engine is a simulator: its rules and recommendation text are canned from the manifest (`stub`), and the write-back is always a dry run.
- Not built yet: search, workflow start/queue/approve (phases 4 and 5; table and document adapters), MCP `tools/call`.

## Single sign-on (`AGENCY_PUBLIC_URL`)

Off unless `AGENCY_PUBLIC_URL` names the address browsers use to reach the layer (for example `https://agency.example.com`). The Server must have its Ask-app OIDC settings (`OMNIGATE_APP_OIDC_*` or the admin console's `OMNIGATE_AUTH_OIDC_*`); the layer asks `/app/auth-config` and shows "Continue with <provider>" on the sign-in page only when the Server says it is on.

The Server sets its session cookie on whoever finishes the provider's callback, and the layer must hold that cookie, so the layer relays the flow instead of sending the browser to the Server: `GET /sso/login` calls the Server's `/app/oidc/login` with `Host` set to `AGENCY_PUBLIC_URL`'s host (the Server builds the provider's redirect address from it), remembers the Server's state cookie against a short-lived, HttpOnly, SameSite=Lax `agency_sso` cookie, and redirects to the provider. The provider returns to `AGENCY_PUBLIC_URL/app/oidc/callback` (**register that address with the provider**); the layer checks the binding cookie and the state, forwards the answer to the Server, keeps the Server's session cookie, and sets `agency_session`. The Server still decides who may sign in (the user must exist as a single-sign-on user, and groups become roles): an unknown person lands on the sign-in page with "no OmniGate account for you". No token or Server cookie reaches the browser.
